## 3. Global Hard Rules (apply to every file)

These override anything that looks locally convenient in any individual file.

1. **Never trust a client-supplied `workspaceId` without a membership check.** Every route that reads `x-workspace-id` from headers must verify `req.user.id` is a member of that workspace before using it in a query. This is the single most repeated defect across the codebase — treat it as a pattern to search for, not just a list of five call sites.
2. **Preserve the soft-delete contract.** This codebase uses `deletedAt: Date | null` as its recovery mechanism everywhere. Any fix that calls `.delete(...)` where the model has a `deletedAt` column is wrong unless the audit explicitly says "hard delete is intentional here." When in doubt, soft-delete.
3. **Scope every query by `workspaceId` and, where the data is personal, by `userId` too.** Multi-tenant leaks in this codebase come from omitting one of these two filters, not from a missing auth check.
4. **Do not introduce new dependencies to fix a bug that has a same-library fix available.** E.g. do not add a new Redis client, a new HTTP client, a new validation library — the existing `ioredis`, `fetchApi`, and `zod` usage already cover every fix in this set.
5. **Do not rewrite a whole file when a targeted patch fixes the issue.** Every fix below is scoped to specific lines. Minimal diffs only — this codebase is being stabilized, not rearchitected.
6. **Do not "helpfully" also fix an issue that isn't listed.** If you notice something else wrong while in a file, log it as a comment (`// TODO(audit): <description>`) and move on. Scope creep during a remediation pass is how regressions get introduced.
7. **Every fix that touches a controller or route must be verified against the exact reproduction steps given in that issue's "Verify" block before being considered done.** "It compiles" is not verification.
8. **Money-shaped and privacy-shaped fields never get logged.** None of these fixes require it, but if a fix path touches logging, do not add `console.log` of full request bodies, tokens, or user records.

---

## 4. Cross-Cutting Themes (read once, recognize everywhere)

- **The `x-workspace-id` header is trusted blindly in ~6 separate routes.** Files 01, 02, and 04 each fix one or more instances of this same defect. It is the same bug, six times.
- **`CANCELED` (one L) is the schema enum; `CANCELLED` (two Ls) appears in frontend string comparisons and silently fails.** Fixed once in file 04, but grep the whole `apps/web` tree for `'CANCELLED'` before declaring this done — the audits found it in two places (`TodayView.tsx`, `SprintView.tsx` logic) and it may exist elsewhere.
- **Prisma's `update`/`delete` `where` clause must reference a field that is actually unique** (`@id` or `@@unique`). The `Milestone` bug in file 06 is one instance of this; if you encounter Prisma runtime validation errors elsewhere during testing, this is the first thing to check.
- **`socketService.emitToUser()` exists and works — it is simply never called.** Files 08 and 11 both rely on this. Do not build a parallel notification mechanism; wire into this one.
- **Soft-deleted rows keep participating in unique constraints, RAG search, and joins because filters forget `deletedAt: null`.** This exact class of bug appears in file 05 (RAG retriever), file 06 (daily log P2002), and file 03 (RAG again). Treat "does this query filter deletedAt?" as a standing checklist item on every query you touch.

# 01 — Authentication & Multi-Tenant Workspace Architecture

**Priority:** P0 (2.1 blocks core multi-workspace usage) · P2 (UI gap)
**Depends on:** `12-DATABASE-SCHEMA-MIGRATIONS.md` §12.2 (expanded `userAuthSelect`)
**Touches:** `apps/web/src/contexts/AuthContext.tsx`, `apps/server/src/utils/selectors.ts`, `apps/web/src/components/Sidebar.tsx`, `apps/web/src/components/AppShell.tsx`

---

## 1. Scope

Fix the bootstrap logic that silently discards the user's saved workspace choice on every reload, add the missing workspace-switcher UI, and clean up token/identity leakage on logout. This is a client-state bug, not a backend data bug — the backend already supports multi-workspace membership correctly.

## 2. Hard Rules for This Section

- Do not change the JWT payload shape (`{ sub, sessionId, email, name }`). Every downstream `req.user!.id` read depends on `sub` staying the userId.
- Do not remove `krama_refresh` httpOnly cookie handling or move the refresh token into localStorage/JS-accessible storage. It is httpOnly by design.
- `switchWorkspace(id)` must remain the single source of truth for changing active workspace — do not create a second code path that sets `krama_active_workspace` directly from a component.

---

## 3. AUTH-01 — Multi-Workspace Reload Trap (Ref: Audit §2.1)

**Symptom:** User switches workspace, page reloads, user is silently returned to their first workspace every time.

**Root cause:** `AuthContext.tsx` bootstrap runs:
```ts
let wid = meData.user.memberships?.[0]?.workspaceId || null;
if (!wid) {
  const savedWid = localStorage.getItem('krama_active_workspace');
  wid = savedWid || null;
}
```
`memberships[0]` is truthy for any valid user, so the `if (!wid)` branch that reads the saved workspace **never executes**. Compounding this: `switchWorkspace` is never called anywhere in `apps/web` — there is no UI that invokes it (see AUTH-02).

**File:** `apps/web/src/contexts/AuthContext.tsx`, lines 98–105 (bootstrap) and 142–149 (logout).

**Fix — replace the bootstrap workspace-resolution block:**
```tsx
const savedWid = localStorage.getItem('krama_active_workspace');
const memberships = meData.user.memberships || [];
const hasSavedMembership = memberships.some((m: any) => m.workspaceId === savedWid);
const wid = (hasSavedMembership ? savedWid : null) || memberships[0]?.workspaceId || null;

api.setWorkspaceId(wid);
if (wid) localStorage.setItem('krama_active_workspace', wid);
```
The saved ID now wins whenever it still corresponds to a real membership; it only falls back to the first membership if the saved one is stale (e.g. the user was removed from that workspace).

**Fix — logout cleanup**, same file, `logout()` / `onGlobalLogout()`:
```tsx
const handleLogout = useCallback(async () => {
  try {
    if (authState.status === 'authed') {
      await api.auth.logout();
    }
  } catch (err) {
    console.error('Logout error', err);
  } finally {
    api.setAccessToken(null);
    api.setWorkspaceId(null);
    localStorage.removeItem('krama_active_workspace');
    localStorage.removeItem('krama_user');
    setAuthState({ status: 'anon' });
  }
}, [authState]);
```
This closes the "tokens leak in memory on logout" and "unread `krama_user` in localStorage" findings from the audit's health matrix in one pass — both were caused by logout not clearing state it had accumulated.

**Verify:**
1. Log in with a user that belongs to 2+ workspaces.
2. Switch to the second workspace (once AUTH-02 below adds the UI to do this).
3. Reload the page (`F5`). Confirm the active workspace is still the second one, not the first membership.
4. Log out. Confirm `localStorage` contains no `krama_active_workspace` or `krama_user` keys and `api.currentAccessToken` is `null`.

---

## 4. AUTH-02 — Missing Workspace Switcher UI (Ref: Audit §9.1)

**Symptom:** There is no way to switch workspaces in the product at all — `switchWorkspace(id)` exists in `AuthContext.tsx` but is dead code because nothing calls it.

**Files:** `apps/web/src/components/Sidebar.tsx`, `apps/web/src/components/AppShell.tsx`.

**Fix:** Add a workspace-switcher dropdown to the Sidebar header. It must:
- Read `user.memberships` (now including `workspace.name` — see AUTH-03) to render the list.
- Highlight the currently active `workspaceId`.
- Call `switchWorkspace(id)` on selection — do not reimplement the reload/localStorage logic locally; the whole point of AUTH-01's fix is that this is centralized.
- Be reachable from both `Sidebar.tsx` and, if the sidebar can be collapsed, from `AppShell.tsx`'s header, so it's never unreachable.

**Verify:** With 2+ workspace memberships, the dropdown is visible, shows both workspace names (not just the active one), and clicking the inactive one calls `switchWorkspace` and results in AUTH-01's reload landing on the newly selected workspace.

```ts
export const userAuthSelect = {
```

**Verify:** `GET /auth/me` response for a multi-workspace user includes `memberships[].workspace.name` for every membership, not just the active one.

# 02 — Security, IDOR & Multi-Tenant Data Leak Architecture

**Priority:** P1 (all five issues are exploitable by any authenticated user, not just an attacker with special access)
**Depends on:** `12-DATABASE-SCHEMA-MIGRATIONS.md` §12.1 (`TimeBlock.workspaceId`)
**Touches:** `apps/server/src/routes/search.routes.ts`, `sprint.controller.ts`, `workspace.routes.ts`, `space.controller.ts`, `upload.routes.ts`, `middlewares/auth.middleware.ts`

---

## 1. Scope

Close every cross-tenant read/write path found in the audit. The common defect shape: a route trusts `req.headers['x-workspace-id']` or a URL param as the tenant boundary without verifying the authenticated user actually belongs to that tenant. Fix each instance, then verify the underlying `requireWorkspaceRole` middleware is applied everywhere it should be.

## 2. Hard Rules for This Section

- **Every fix in this file is additive (adding a check), never a removal of an existing check.** If you find yourself deleting an auth check to make a test pass, stop — the test is wrong, not the check.
- Use the existing `requireAuth` and `requireWorkspaceRole(role)` middlewares from `middlewares/auth.middleware.ts`. Do not write ad hoc `if (member.role !== 'OWNER')` checks inline when a middleware call does the same thing — consistency here is what makes future audits tractable.
- `requireWorkspaceRole('MEMBER')` means "any role, but must be a member of this workspace" — use it for read paths. `requireWorkspaceRole('OWNER')` is for destructive workspace-level mutations only.

---

## 3. SEC-01 — Global Search Cross-Tenant Data Leak (Ref: Audit §3.1)

**Vulnerability:** `GET /api/v1/search` reads `x-workspace-id` from the header and queries directly — it never checks `req.user.id` is a member of that workspace. Any authenticated user can pass any workspace UUID and read another organization's documents, tasks, projects, and goals.

**File:** `apps/server/src/routes/search.routes.ts`, lines 7–20.

**Fix:**
```ts
import { requireAuth, requireWorkspaceRole } from '../middlewares/auth.middleware';

const router: Router = Router();
router.use(requireAuth);
router.use(requireWorkspaceRole('MEMBER'));
```

**Verify:** As User A (member of Workspace 1 only), call `GET /api/v1/search?q=test` with `x-workspace-id` set to Workspace 2's UUID. Expect `403`, not search results.

---

## 4. SEC-02 — Cross-Tenant Sprint Report IDOR (Ref: Audit §3.2)

**Vulnerability:** `getSprintReport` does `prisma.sprint.findUnique({ where: { id } })` and returns it without checking `sprint.workspaceId` matches the caller's workspace. Anyone who knows or guesses a sprint UUID reads another tenant's burndown, estimates, and velocity.

**File:** `apps/server/src/controllers/sprint.controller.ts`, lines 160–176.

**Fix:**
```ts
const sprint = await prisma.sprint.findUnique({ where: { id } });
if (!sprint || sprint.deletedAt || sprint.workspaceId !== workspaceId) {
  return res.status(404).json({ message: 'Sprint not found' });
}
```
Return `404`, not `403` — do not confirm the sprint's existence to a caller outside its tenant.

**Verify:** As a user outside the sprint's workspace, `GET /sprints/:id/report` returns `404` for a real, existing sprint ID belonging to another tenant.

---

## 5. SEC-03 — Workspace & Space Mutation IDOR (Ref: Audit §3.3)

**Vulnerability:**
- `PATCH /api/v1/workspaces/:id` and `DELETE /api/v1/workspaces/:id` don't require the `OWNER` role — any member can rename or delete the workspace.
- `PUT /api/v1/spaces/:id` and `DELETE /api/v1/spaces/:id` don't filter by `workspaceId` — a space ID from one tenant can be mutated by a member of a different tenant.

**Files:** `apps/server/src/routes/workspace.routes.ts` (lines 20–22), `apps/server/src/controllers/space.controller.ts` (lines 45, 58).

**Fix — workspace routes:**
```ts
router.patch('/:id', requireAuth, requireWorkspaceRole('OWNER'), updateWorkspace);
router.delete('/:id', requireAuth, requireWorkspaceRole('OWNER'), deleteWorkspace);
```

**Before writing the fix below, verify where the tenant ID actually comes from.** None of the source audit material confirms that `req.workspaceId` is a property any existing middleware attaches to the request. The only pattern proven elsewhere in this codebase (see `06-PLANNER-AND-CALENDAR.md` PLAN-01) is reading `x-workspace-id` directly from headers. Check `apps/server/src/middlewares/auth.middleware.ts`:
- **If `requireAuth` or `requireWorkspaceRole` already decorates `req.workspaceId`** (a common pattern, since `requireWorkspaceRole(role)` must itself resolve a workspace ID to check the caller's role in it) — confirm it does so only *after* validating the caller is actually a member, and use it as-is.
- **If no such decoration exists**, do not read `req.headers['x-workspace-id']` and trust it blindly — that is the exact defect this issue exists to close. Instead, resolve and validate it explicitly:
```ts
const requestedWorkspaceId = req.headers['x-workspace-id'] as string;
const membership = await prisma.workspaceMember.findFirst({
  where: { userId: req.user!.id, workspaceId: requestedWorkspaceId },
});
if (!membership) return res.status(403).json({ message: 'Not a member of this workspace' });
const workspaceId = membership.workspaceId;
```
Confirm the actual membership model/table name against the real schema (`WorkspaceMember`, `Membership`, or whatever it's actually called) before using this snippet verbatim.

**Fix — space controller**, both the update and delete handlers, using whichever `workspaceId` resolution above is correct for this codebase:
```ts
const space = await prisma.space.findFirst({
  where: { id: req.params.id, workspaceId },
});
if (!space) return res.status(404).json({ message: 'Space not found' });
// proceed with update/delete using space.id, not req.params.id directly
```
This also lays the groundwork for `05-BRAIN-KNOWLEDGE-BASE.md`'s cascade-deletion fix and `11-FOCUS-MODE-FEATURE.md`'s new endpoints, both of which reuse whichever `workspaceId`-resolution pattern is confirmed correct here — do this one first, and resolve the verification question once, here, rather than re-guessing it in each downstream file.

**Verify:** A `MEMBER`-role user gets `403` on `PATCH /workspaces/:id`. A user from Workspace A gets `404` (not a successful mutation) when calling `PUT /spaces/:id` with a Workspace B space ID.

## 6. SEC-04 — Cross-Workspace Calendar Leak (Ref: Audit §3.4)

**Vulnerability:** `TimeBlock` has `userId` but no `workspaceId`. A user in both a Work and a Personal workspace sees Work timeblocks and project references bleed into their Personal planner view, because nothing scopes the query by workspace at all — only by user.

**Schema fix:** See `12-DATABASE-SCHEMA-MIGRATIONS.md` §12.1 — this file only covers the **application-layer** half.

**Files:** every route in `apps/server/src/routes/planner.routes.ts` that queries or writes `TimeBlock`.

**Fix:** Once the migration adds `TimeBlock.workspaceId`, every `prisma.timeBlock.findMany` / `.create` / `.update` in `planner.routes.ts` must filter/set `workspaceId` in addition to the existing `userId` filter:
```ts
prisma.timeBlock.findMany({
  where: { userId, workspaceId, date: { gte: startOfDay, lte: endOfDay } },
  orderBy: { startTime: 'asc' },
});
```
Grep `planner.routes.ts` for every `prisma.timeBlock.` call and apply the same pattern — this is not a single call site, it is every TimeBlock query in that file.

**Verify:** A user with TimeBlocks in both a Work and a Personal workspace sees only the active workspace's blocks in `/app/planner` week view, regardless of which workspace they switch to.

---

## 7. SEC-05 — Unbounded Memory Uploads (DoS) (Ref: Audit §3.5)

**Vulnerability:** `multer({ storage: multer.memoryStorage() })` has no `limits.fileSize`. Any authenticated user can upload an arbitrarily large stream and OOM-crash the Node process.

**File:** `apps/server/src/routes/upload.routes.ts`, line 8.

**Fix:**
```ts
const upload = multer({
  storage: multer.memoryStorage(),
  limits: { fileSize: 10 * 1024 * 1024 }, // 10MB
});
```
Also add a `multer` error handler (or confirm one exists) that returns `413 Payload Too Large` on `LIMIT_FILE_SIZE`, rather than letting it bubble to a generic 500.

**Verify:** An upload request with a >10MB body returns `413`, and the server process memory does not spike proportionally to attempted upload size.

# 03 — AI Subsystem & RAG Architecture

**Priority:** P0 (3.1 is a total production outage) · P1 (3.3 leaks soft-deleted content) · P2 (3.4/3.5 wire up dead endpoints)
**Touches:** `apps/server/src/services/krama-ai.service.ts`, `narrative.service.ts`, `ai.service.ts`, `apps/server/src/lib/embedding.ts`, `embedding.worker.ts`, `apps/server/src/services/rag/retriever.ts`, `apps/web/src/components/ProjectDetail.tsx`, `apps/web/src/components/planner/DailyLogSection.tsx`

---

## 1. Scope

Restore the AI chat assistant and daily narrative debrief (both are currently 100% broken in production), fix the embedding pipeline crash, stop leaking trashed documents into RAG context, and connect two already-built backend AI features to real UI instead of leaving them orphaned.

## 3. PLAN-01 — Daily Log Creation Crash: Missing `workspaceId` (Ref: Audit §2.4)

**Symptom:** Any attempt to record a daily log from `/app/planner` crashes with `400 Validation failed: workspaceId Required`.

**Root cause:** `CreateDailyLogSchema` requires `workspaceId`. The frontend mutation payload in `DailyLogSection.tsx` omits it, and the controller does `CreateDailyLogSchema.parse(req.body)` directly, without injecting it from the `x-workspace-id` header.

**Fix — this also resolves PLAN-02 (P2002) in the same handler, since both live in `createDailyLog`:**
```ts
export const createDailyLog = async (req: Request, res: Response) => {
  try {
    const workspaceId =
      (req.headers['x-workspace-id'] as string) ||
      (req.query.workspaceId as string) ||
      req.body.workspaceId;
    if (!workspaceId) return res.status(400).json({ message: 'workspaceId is required' });

    const data = CreateDailyLogSchema.parse({ ...req.body, workspaceId });
    const logDate = new Date(data.date);
    logDate.setUTCHours(12, 0, 0, 0); // canonical UTC noon prevents timezone-boundary shifts

    const existing = await prisma.dailyLog.findFirst({
      where: { workspaceId, userId: req.user!.id, date: logDate },
    });

    if (existing) {
      if (!existing.deletedAt) {
        return res.status(409).json({ message: 'Log already exists for this date. Use PATCH to update.' });
      }
      const resurrected = await prisma.dailyLog.update({
        where: { id: existing.id },
        data: { ...data, deletedAt: null, updatedBy: req.user!.id },
      });
      return res.status(200).json(resurrected);
    }

    const log = await prisma.dailyLog.create({
      data: { ...data, date: logDate, userId: req.user!.id, createdBy: req.user!.id },
    });
    return res.status(201).json(log);
  } catch (error: any) {
    if (error.name === 'ZodError') {
      return res.status(400).json({ message: 'Validation failed', errors: error.errors });
    }
    return res.status(500).json({ message: 'Internal server error' });
  }
};
```
Note the `findFirst` here deliberately does **not** filter `deletedAt: null` — that's the fix for PLAN-02 below; it needs to see soft-deleted rows to resurrect them.

## 5. PLAN-03 — Milestone Update/Delete Prisma Validation Error (Ref: Audit §6.3)

**Symptom:** Updating or deleting any milestone throws a Prisma Client runtime validation error.

**Root cause:**

Prisma's `where` on `update`/`delete` must reference a field that is actually `@id` or part of an `@@unique`. `Milestone` only has `@id` on `id` — there is no compound unique on `(id, userId)`, so passing both fields in `where` is invalid at the Prisma Client level, not just a logic bug.

**File:** `apps/server/src/routes/planner.routes.ts`, lines 498 and 515.

**Fix — resolve ownership first with `findFirst`, then mutate by the bare `id`:**
```ts

  try {
    const userId = getUserId(req);
    if (!userId) return res.status(401).json({ message: 'Unauthorized' });

    const existing = await prisma.milestone.findFirst({ where: { id: req.params.id as string, userId } });
    if (!existing) return res.status(404).json({ message: 'Milestone not found' });

    const schema = z.object({
      title: z.string().min(1).optional(),
      date: z.coerce.date().optional(),
      projectId: z.string().min(1).optional(),
      completed: z.boolean().optional(),
    });
    const body = schema.parse(req.body);
    const dataToUpdate: any = { ...body };
    if (body.date) dataToUpdate.date = startOfDay(body.date);

    const milestone = await prisma.milestone.update({ where: { id: existing.id }, data: dataToUpdate });
    return res.json(milestone);
  } catch (error) {
    return res.status(400).json({ message: 'Unable to update milestone' });
  }
});

router.delete('/milestones/:id', async (req: Request, res: Response) => {

});
```

# 08 — Real-Time Event Bus Architecture

**Priority:** P1 (the entire multi-tab/multi-user real-time layer is currently dead)
**Depends on:** nothing structural — `socketService.emitToUser()` already exists and works.
**Read before Focus Mode:** `11-FOCUS-MODE-FEATURE.md` §11 depends on this pattern being proven functional; do this file first.
**Touches:** `apps/server/src/events/subscribers.ts`, `apps/server/src/workers/notifications.worker.ts`, `apps/web/src/providers/SocketProvider.tsx`

---

## 1. Scope

Wire the already-built domain event bus to the already-built `socketService.emitToUser()`, so that task creation/update/deletion and notifications actually reach connected clients in real time. Currently, `focus:session:completed` is the *only* socket event ever emitted server-side — everything `SocketProvider.tsx` listens for (`task:created`, `task:updated`, `task:deleted`, `notification`) has no emitter.

## 2. Hard Rules for This Section

- Do not build a second real-time mechanism (SSE, polling-with-shorter-interval, etc.) as a workaround. `socketService.emitToUser()` and the Redis pub/sub adapter behind it already work — this is purely a "call the function that already exists" fix.
- Every domain event subscriber added here must guard on `payload.userId` being present before emitting — do not emit to an undefined user ID.
- `NotificationCenter`'s 30-second poll should be **removed or significantly lengthened as a fallback only** once real-time delivery is confirmed working — do not leave both a tight poll and real-time delivery running simultaneously as the permanent state; that defeats the purpose of this fix and doubles server load.

---

## 3. RT-01 — Dead Real-Time Socket.io Event Bus (Ref: Audit §4.1)

**Symptom:** `task:created`, `task:updated`, `task:deleted`, and `notification` are listened for client-side but never emitted server-side anywhere except the single unrelated `focus:session:completed` event. Multi-tab Kanban sync and instant notifications are completely non-functional; the client silently falls back to whatever manual-reload or polling behavior exists.

**Files:** `apps/server/src/events/subscribers.ts` (task events), `apps/server/src/workers/notifications.worker.ts` (notification events).

**Fix — `subscribers.ts`:**
```ts
import { domainEventBus } from './eventBus';
import { socketService } from '../services/socket.service';

domainEventBus.onEvent('TASK_CREATED', (payload: any) => {
  if (payload.userId) socketService.emitToUser(payload.userId, 'task:created', payload);
});

domainEventBus.onEvent('TASK_UPDATED', (payload: any) => {
  if (payload.userId) socketService.emitToUser(payload.userId, 'task:updated', payload);
});

domainEventBus.onEvent('TASK_DELETED', (payload: any) => {
  if (payload.userId) socketService.emitToUser(payload.userId, 'task:deleted', payload);
});
```

Before wiring this, confirm `domainEventBus.onEvent('TASK_CREATED', ...)` etc. are actually the correct event names the domain layer emits when tasks are created/updated/deleted — grep for where tasks are mutated (task controller/service) and confirm each mutation path actually publishes these events to `domainEventBus` in the first place. If a mutation path doesn't publish the event yet, that mutation path needs the `domainEventBus.emit('TASK_UPDATED', { userId, ...task })` call added at its own call site — this file's fix only wires the *subscriber* side; if the *publisher* side is also missing for a given mutation, fix that at the mutation's own controller, not here.

**Fix — `notifications.worker.ts`:** wherever a `Notification` row is created for a user, add:
```ts
socketService.emitToUser(notification.userId, 'notification', notification);
```
immediately after the row is persisted.

**Verify:**
1. Open the Kanban board in two browser tabs, same user, same workspace.
2. Create or update a task in tab 1.
3. Confirm tab 2 reflects the change without a manual reload, within roughly a second.
4. Trigger a notification-generating action (whatever the product's existing notification triggers are). Confirm it appears in `NotificationCenter` in real time, not on the next 30-second poll cycle.

---

## 4. RT-02 — `NotificationCenter` 30-Second Poll Should Become a Fallback, Not the Primary Path

**Symptom (consequence of RT-01 being dead):** `NotificationCenter` polls every 30 seconds because real-time delivery never worked. Once RT-01 is fixed, this poll is redundant load.

**Fix:** Keep a poll as a resilience fallback (sockets do disconnect), but lengthen the interval substantially (e.g. every 2–5 minutes) once real-time delivery is confirmed working, and/or trigger an immediate refetch on socket reconnect rather than relying on the interval alone.

**Verify:** With sockets connected, notifications arrive in real time (per RT-01's verification). Disconnect the socket (e.g. via devtools network throttling) and confirm the fallback poll still eventually surfaces a new notification, so users on a flaky connection aren't left with nothing.

---

## 5. Cleanup

None — this file is purely additive (wiring existing pieces together).

## 6. Section Completion Checklist

- [ ] `TASK_CREATED`/`TASK_UPDATED`/`TASK_DELETED` domain events reach connected clients via `socketService.emitToUser` (RT-01).
- [ ] Confirmed the publisher side (domain event emission at the actual task mutation call sites) exists for all three event types — not just the subscriber wiring (RT-01).
- [ ] Notification creation emits a real-time `notification` socket event (RT-01).
- [ ] `NotificationCenter`'s poll interval is lengthened to a fallback cadence, not left at 30s as the primary delivery mechanism (RT-02).
- [ ] Multi-tab sync manually verified for both task changes and notifications.

## 1. Scope

## 2. Hard Rules for This Section

## 3. DASH-01 — Dashboard OOM Hazard & Cross-User Focus Session Leak (Ref: Audit §7.1)

**Symptom:** Two separate defects in the same controller:
1. `prisma.document.findMany({ where: { space: { workspaceId }, deletedAt: null } })` has no `select`, so it loads every document's full TipTap JSON and markdown body into Node memory — purely to compute `pages.length` for a dashboard stat card. On a workspace with many/large documents, this is an OOM risk.
2. `prisma.focusSession.findMany({ where: { workspaceId } })` does not filter by `userId` — every workspace member's focus sessions (including duration, task, timing) are returned and rendered on every other member's dashboard.

**File:** `apps/server/src/controllers/dashboard.controller.ts`, lines 28 and 31.

**Fix:**
```ts
const [
  workspace, projects, tasks, habits, noteCount, dailyLogs, focusSessions, activityLogs, goals,
] = await Promise.all([
  prisma.workspace.findUnique({ where: { id: workspaceId } }),
  prisma.project.findMany({ where: { workspaceId, deletedAt: null }, orderBy: { updatedAt: 'desc' } }),
  prisma.task.findMany({ where: { workspaceId, deletedAt: null }, orderBy: { updatedAt: 'desc' } }),
  prisma.habit.findMany({ where: { workspaceId, deletedAt: null }, orderBy: { updatedAt: 'desc' }, include: { completions: true } }),
  // Count instead of loading full document bodies into memory:
  prisma.document.count({ where: { space: { workspaceId }, deletedAt: null } }),
  prisma.dailyLog.findMany({ where: { workspaceId, deletedAt: null }, orderBy: { date: 'desc' }, take: 14 }),
  // Scope to the requesting user — do not leak other members' sessions:
  prisma.focusSession.findMany({ where: { workspaceId, userId: req.user!.id }, orderBy: { createdAt: 'desc' } }),
  prisma.activityLog.findMany({ where: { workspaceId }, orderBy: { createdAt: 'desc' }, take: 20 }),
  prisma.goal.findMany({ where: { workspaceId, deletedAt: null } }),
]);
```
Note `activityLog` here is intentionally workspace-scoped rather than user-scoped — confirm against product intent whether the activity feed is meant to show the whole team's activity (likely, for a team dashboard) or only the current user's; the audit doesn't flag `activityLog` as a leak, only `focusSession`, so leave it workspace-scoped unless told otherwise.

**Verify:** Load the dashboard for a workspace with large documents — confirm memory usage doesn't spike proportional to document body size (the count query should be near-constant time/memory regardless of document size). As User A, confirm the dashboard's focus session card shows only User A's sessions, not User B's, even though both are in the same workspace.

# 11 — Focus Mode: Full-Screen Timer Feature Architecture

**Priority:** New feature (additive) — build last, after files 01–10.
**Depends on:** `08-REALTIME-EVENTS.md` (proves `socketService.emitToUser` pattern works before this file adds a second consumer of it), `01-AUTH-AND-WORKSPACE.md` (auth bootstrap must be reliable before a second tab depends on it).
**Status of underlying data:** No DB migration required — every field this feature reads already exists (`FocusSession`, `Task.estimateMinutes`, `TimeBlock`, `User.weeklyCapacityMinutes`). See §10 (Data Sources).

---

## 1. Feature Summary

A full-screen `/focus` tab, opened via `Ctrl+Shift+Q` from anywhere in the app, running one of two modes:
- **Manual Mode** — user picks a duration and runs a plain pomodoro/break timer.
- **Planner Mode** — the backend computes an optimized pomodoro sequence from today's `TimeBlock`s and `Task.estimateMinutes`, capped by `User.weeklyCapacityMinutes / 5` minus meeting time.

Two build phases in this file: **Phase A** (§§2–9) is the base feature. **Phase B** (§10) is a borderless/native-feeling refactor that must land on top of Phase A, not replace it mid-build — finish Phase A, verify it, then apply Phase B.

---

## 2. Hard Rules for This Feature

1. **Do not read `localStorage.getItem('krama_token')` anywhere in new code.** This key is never written anywhere in the codebase — `SocketProvider.tsx` reads it and always gets `null`, a pre-existing latent bug unrelated to this feature. FocusPage's own socket connection must use the **in-memory** `accessToken` from `useAuth()`, obtained via `AuthContext.bootstrap()`'s `POST /auth/refresh` call against the httpOnly `krama_refresh` cookie. Do not replicate the broken pattern in new code, even though it exists elsewhere.
2. **Reuse existing backend services — do not rebuild them.** `calculateCapacity()`, `analyticsService.getFocusHistory()`, `socketService.emitToUser()`, `redisService.get/set()`, `aiService`, the R2 upload pipeline, and `api.auth.updatePreferences()` all already exist and are confirmed working. This feature is new orchestration on top of them, not a parallel implementation.
3. **`api.focusSessions` already exists** in `apps/web/src/api/client.ts` at line 349 with a `complete()` method. Add `getSchedule()` and `getWallpaper()` to that same object — do not create a second namespace.
4. **`User.metadata.timerPreferences`** already exists and is typed in `AuthContext.tsx:10` as `{ sprint, deep, quick }`. Extend it with the new fields (`focusDuration`, `shortBreak`, `longBreak`, `longBreakAfter`) — do not create a new, separate preferences structure.
5. **JWT payload uses `payload.sub` for user ID**, exposed to handlers as `req.user!.id` via `requireAuth`. Use it exactly as `completeFocusSession` already does — no new auth-parsing logic.
6. **No DB migration for this feature.** If you find yourself wanting to add a column to support Focus Mode, stop — re-read §10 (Data Sources); the data you need already exists somewhere in the current schema.

---

## 3. Architecture Overview

```
Ctrl+Shift+Q (anywhere in the app, via AppShell's existing keydown handler)
        │
        ▼
window.open('/focus', '_blank')
        │
        ▼
FocusPage.tsx — new route, INSIDE <AuthGuard> in App.tsx (same guard as /app/*)
  ├── useAuth() — AuthProvider already wraps the whole app (main.tsx), no new provider needed
  ├── own Socket.IO connection (SocketProvider only wraps /app/*, this is a separate tab)
  ├── GET /focus-sessions/schedule → today's plan
  ├── state machine: IDLE → RUNNING → PAUSED → COMPLETED
  ├── POST /focus-sessions on each completed slot (existing endpoint, unchanged)
  └── 5 swappable timer layouts + wallpaper system
```

---

## 4. Backend: `focusTimer.service.ts` (New)

**File:** `apps/server/src/services/focusTimer.service.ts`

Implements `buildFocusSchedule(userId, workspaceId, prefs)`. Full algorithm:

```typescript
interface TimerPreferences {
  focusDuration: number;   // default 25
  shortBreak: number;      // default 5
  longBreak: number;       // default 15
  longBreakAfter: number;  // default 4
}

interface SessionSlot {
  index: number;
  type: 'pomodoro' | 'short_break' | 'long_break';
  durationMin: number;
  taskId: string | null;
  taskTitle: string | null;
  projectId: string | null;
  projectName: string | null;
  label: string;
  timeBlockId: string | null;
  scheduledStart?: string;
}

async function buildFocusSchedule(userId: string, workspaceId: string, prefs: TimerPreferences) {
  // STEP 1 — load today's data in parallel
  const today = new Date();
  const startOfDay = new Date(today); startOfDay.setHours(0, 0, 0, 0);
  const endOfDay = new Date(today);   endOfDay.setHours(23, 59, 59, 999);

  const [user, timeBlocks, tasks, completedSessions] = await Promise.all([
    prisma.user.findUnique({ where: { id: userId }, select: { weeklyCapacityMinutes: true } }),
    prisma.timeBlock.findMany({
      where: { userId, workspaceId, date: { gte: startOfDay, lte: endOfDay } }, // workspaceId per 02-SECURITY-AND-IDOR.md SEC-04
      orderBy: { startTime: 'asc' },
    }),
    prisma.task.findMany({
      where: {
        workspaceId, deletedAt: null, status: { not: 'DONE' },
        OR: [
          { scheduledDate: { gte: startOfDay, lte: endOfDay } },
          { dueDate: { gte: startOfDay, lte: endOfDay } },
        ],
      },
      orderBy: [{ priority: 'desc' }, { dueDate: 'asc' }],
    }),
    prisma.focusSession.findMany({
      where: { userId, workspaceId, startTime: { gte: startOfDay }, completed: true },
    }),
  ]);

  // STEP 2 — daily cap, net of meetings (calculateCapacity already merges intervals)
  const dailyCapMinutes = Math.round((user?.weeklyCapacityMinutes ?? 2400) / 5);
  const capacity = calculateCapacity(user?.weeklyCapacityMinutes ?? 2400, timeBlocks);
  const effectiveDailyCapMinutes = Math.max(0, dailyCapMinutes - capacity.meetingMinutes);
  const alreadyLoggedMinutes = completedSessions.reduce((sum, s) => sum + Math.round(s.duration / 60), 0);
  const remainingMinutes = Math.max(0, effectiveDailyCapMinutes - alreadyLoggedMinutes);

  // STEP 3 — work slots from TimeBlocks (STUDY, WORK, OTHER types contribute; MEETING/PERSONAL already deducted above)
  const focusBlockTypes = ['STUDY', 'WORK', 'OTHER'];
  const workBlocks = timeBlocks.filter(b => focusBlockTypes.includes(b.type));
  const taskMap = new Map(tasks.map(t => [t.id, t]));

  const workSlots = workBlocks.map(block => {
    const blockDuration = Math.round((block.endTime.getTime() - block.startTime.getTime()) / 60000);
    const linkedTask = block.taskId ? taskMap.get(block.taskId) : null;
    return {
      blockId: block.id, durationMin: blockDuration,
      taskId: linkedTask?.id ?? null, taskTitle: linkedTask?.title ?? block.title,
      projectId: block.projectId ?? linkedTask?.projectId ?? null,
      scheduledStart: block.startTime.toISOString(),
    };
  });

  // Fallback: no TimeBlocks scheduled today → synthesize slots from top 5 tasks by estimateMinutes
  if (workSlots.length === 0 && tasks.length > 0) {
    for (const task of tasks.slice(0, 5)) {
      workSlots.push({
        blockId: `synthetic-${task.id}`, durationMin: task.estimateMinutes ?? prefs.focusDuration,
        taskId: task.id, taskTitle: task.title, projectId: task.projectId ?? null,
        scheduledStart: new Date().toISOString(),
      });
    }
  }

  if (workSlots.length === 0) {
    return { mode: 'empty', plan: [], totalFocusMinutes: 0, dailyCapMinutes, alreadyLoggedMinutes, remainingMinutes, taskBreakdown: [] };
  }

  // STEP 4 — expand into pomodoro + break cycles
  const plan: SessionSlot[] = [];
  let globalIndex = 0, globalPomodoroCount = 0, totalFocusMinutes = 0;
  const taskBreakdown: { taskId: string; title: string; pomodoroCount: number }[] = [];

  for (const slot of workSlots) {
    const effectiveDuration = slot.taskId && taskMap.get(slot.taskId)?.estimateMinutes
      ? taskMap.get(slot.taskId)!.estimateMinutes! : slot.durationMin;
    const pomodoroCount = Math.max(1, Math.ceil(effectiveDuration / prefs.focusDuration));

    if (slot.taskId) taskBreakdown.push({ taskId: slot.taskId, title: slot.taskTitle ?? '', pomodoroCount });

    for (let p = 0; p < pomodoroCount; p++) {
      plan.push({
        index: globalIndex++, type: 'pomodoro', durationMin: prefs.focusDuration,
        taskId: slot.taskId, taskTitle: slot.taskTitle, projectId: slot.projectId, projectName: null,
        label: slot.taskTitle ?? 'Focus',
        timeBlockId: slot.blockId.startsWith('synthetic') ? null : slot.blockId,
        scheduledStart: slot.scheduledStart,
      });
      totalFocusMinutes += prefs.focusDuration;
      globalPomodoroCount++;

      const isLastPomodoro = p === pomodoroCount - 1 && slot === workSlots[workSlots.length - 1];
      if (!isLastPomodoro) {
        const isLongBreak = globalPomodoroCount % prefs.longBreakAfter === 0;
        plan.push({
          index: globalIndex++, type: isLongBreak ? 'long_break' : 'short_break',
          durationMin: isLongBreak ? prefs.longBreak : prefs.shortBreak,
          taskId: null, taskTitle: null, projectId: null, projectName: null,
          label: isLongBreak ? 'Long Break' : 'Short Break', timeBlockId: null,
        });
      }
    }
  }

  // STEP 5 — enforce daily cap, trim tail
  let plannedSoFar = 0;
  const cappedPlan: SessionSlot[] = [];
  for (const slot of plan) {
    if (slot.type === 'pomodoro') {
      if (plannedSoFar + slot.durationMin > remainingMinutes) break;
      plannedSoFar += slot.durationMin;
    }
    cappedPlan.push(slot);
  }
  cappedPlan.forEach((s, i) => { s.index = i; });

  return { mode: 'planner', plan: cappedPlan, totalFocusMinutes: plannedSoFar, dailyCapMinutes, alreadyLoggedMinutes, remainingMinutes, taskBreakdown };
}
```

**Cache strategy:** wrap the return value with `redisService.set('focus:schedule:${userId}', JSON.stringify(result), 300)` (5-minute TTL). Invalidate this key inside `completeFocusSession` right after a session is saved, so the next schedule fetch reflects updated `remainingMinutes`.

## 3. §12.1 — Add `TimeBlock.workspaceId` (Ref: Audit §3.4, `02-SECURITY-AND-IDOR.md` SEC-04)

**Why:** `TimeBlock` currently has only `userId`, so a user in two workspaces sees calendar data bleed across them. This is a security/correctness fix, not just a feature.

**Schema change:**
```prisma
model TimeBlock {
  // ...existing fields...
  workspaceId String
  workspace   Workspace @relation(fields: [workspaceId], references: [id])
  // ...existing indexes...
  @@index([workspaceId, userId, date])
}
```

**Backfill required:** existing `TimeBlock` rows have no `workspaceId`. Before making the column `NOT NULL`:
1. Add the column as nullable first.
2. Backfill: for each existing `TimeBlock`, set `workspaceId` from the linked `User`'s **default/first workspace membership** (or, if `TimeBlock` has any other field that indirectly implies a workspace — e.g. a linked `Task.workspaceId` via `taskId` — prefer that as a more accurate source than "first membership"). Confirm which backfill source is actually correct against the real data before running it against production; a wrong backfill here silently assigns TimeBlocks to the wrong workspace, which is the exact class of bug this migration exists to fix.
3. Once backfilled and verified with zero remaining NULLs, alter the column to `NOT NULL` in a follow-up migration step.

**Application-layer dependency:** every `prisma.timeBlock.*` call across `planner.routes.ts` (and the new Focus Mode service in file 11) must be updated to filter/set `workspaceId` once this lands — that work is specified in `02-SECURITY-AND-IDOR.md` §SEC-04, not here; this section is schema-only.
